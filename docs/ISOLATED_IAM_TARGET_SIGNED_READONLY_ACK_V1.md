# #2379 — Target-owned signed read-only mTLS acknowledgement V1

**Scope: synthetic disposable single-host IAM only. The target's signing key
is generated by the test HOST; target-only mounting is NOT independent key
custody or independent operator governance. No production PROVEN status.**

## Difference from #2377–#2378

Earlier demos reconcile by the trusted test-host **opening target-owned SQLite
files directly**, even though Docker mTLS controls the original mutation.
#2379 removes that direct target-DB access **from the new independent
read-only acknowledgement verifier**, not yet from every legacy audit step.

## Actual test boundary

1. Existing VERITAS native signed approval → real **PostgreSQL** atomic
   single-use consumption → effect-bound signed Permit → **Docker mTLS** POST
   to the target → exactly one target-owned SQLite synthetic IAM role grant.
2. Before starting target, the disposable host generates a **separate Ed25519
   target receipt signer**. Its private key is mounted read-only ONLY in the
   target container; it is not the native issuer signing key and is never
   available inside the reader or agent containers. Public PEM is distributed
   to the new read-only reader. Host sees this key during generation, so
   signing custody **is not independently operated**.
3. An opt-in target endpoint
   `GET /v1/iam/reconciliation/{percent-encoded-permit-id}` is available
   ONLY with `LAB_TEST_READONLY_ACK=1`. A **distinct** CA-verified
   `CN=reconciliation-reader` certificate is required; a scoped-executor
   certificate is intentionally refused. The reader is a separate Docker
   service with **no SQLite, execution Permit, or target signer key mount**.
4. Target queries its own SQLite *read-only* for exactly one committed target
   grant/permit-use/audit. Only confirmed positive status is signed, using
   canonical JSON and Ed25519. An unknown reference yields HTTP 404, **never
   a signed CONFIRMED_NO_EFFECT**.
5. A separate reader Docker container fetches the signed response over
   genuine TLS and verifies the target public key. Bad cert, authorized
   mutator without read permission, and nonexistent operation all fail.
6. An isolated host-side verifier checks the independent signed target
   response again; it does **not** open the target SQLite. The original
   native Permit is verified with the **different native issuer public key**,
   target response content is tied to exact authorization/intent/request
   lineage, target commit timestamp falls within original Permit validity,
   and existing native **PostgreSQL** consumption is checked.
7. The host's original #2376 fixture verifier STILL performs direct SQLite
   checks separately to independently establish this bounded test's actual
   target effect. This is not the authority for the new signed-only verifier.

The original Docker permit flow, native security policy, and #2375–#2378
workflows remain unchanged when `LAB_TARGET_READONLY_ACK=0`. New mode is
explicitly opt-in alongside `LAB_NATIVE_DURABLE_PG=1`, with the normal
known-response flow (`LAB_NATIVE_LOST_ACK=0`).

## Failure and refusal semantics

- **403:** client certificate valid but not the distinct reader identity.
- **mTLS handshake denied:** no client certificate.
- **404:** unknown operation or unconfirmed target effect. Cannot be turned
  into "confirmed no effect," a new authorization, or a replay.
- **503:** target DB unavailable or target signer unavailable.
- **Fail closed:** mismatching target signature, signer key, Permit ID,
  authorization ID, execution intent, request ID, signed status, actor,
  grant, timestamp, source identity or PostgreSQL consumption.

The new evidence is signed positive observation; it is **not** an independent
audit, production authorization, or complete remote Reconciliation.

## What is NOT proven

- The trusted host generated **both** test signing credentials, so no
  separately operated key custody, third-party attestation or cross-operator
  trust exists.
- The service and reader are separate Docker containers, **not separate
  physical hosts or independent companies**. Runtime network separation
  is Docker-only and the host controls both volumes.
- #2379 does not apply the new signed acknowledgement to the existing
  `EFFECT_UNKNOWN -> CONFIRMED_EFFECT` CAS. That should be a separate,
  independently tested #2380 using the existing state machine. It does
  not remove legacy same-host direct SQLite auditing from #2377/#2378.
- No cloud IAM operation, real customer, paid provider, official AgentDojo
  Utility scorer, host network partition, production signer hardware,
  real attack-surface certificate revocation, `ALLOW_01 PROVEN` or
  `RECON_01 PROVEN`.
